### 背景

当前 `D:\GitHub\shells\ps` 下已有一套 PowerShell 脚本，用于在 Windows 上启用 OpenSSH Server、放行防火墙、写入用户公钥，并在可用时启动 `cpolar tcp 22` 做端口映射。目标是将这套能力迁移到 `D:\GitHub\pythontools\others`，以单文件 Python 工具的形式提供等价功能。

### 目标

- 在 `D:\GitHub\pythontools\others` 新增单文件 Python 脚本 `start_ssh.py`

- 保持交互式使用方式，不强制要求命令行参数

- 保持与原 PowerShell 脚本等价的核心行为：

    - 检查并安装 `OpenSSH.Server~~~~0.0.1.0`

    - 启动 `sshd` 服务并设置为自动启动

    - 确保存在名为 `sshd` 的入站防火墙规则，放行 TCP 22

    - 提示用户输入 SSH 公钥，并写入当前用户的 `~/.ssh/authorized_keys`

    - 保留原有 `cpolar` 行为：未安装时打开官网，已安装但未运行 `tcp 22` 时自动启动

- 非管理员运行时，明确提示并直接退出

### 非目标

- 不将脚本改造成多文件模块化项目

- 不额外引入 GUI

- 不在本次迁移中增加通用参数模式，例如 `--check-only` 或 `--skip-cpolar`

- 不做完整系统级自动化测试，避免在测试中修改本机 SSH 服务和防火墙状态

### 方案对比

#### 方案一：单文件交互式 Python 脚本

这是推荐方案。脚本结构接近 `others` 目录下现有工具风格，用户直接运行即可，所有关键输入通过交互完成。系统配置相关操作仍通过 Python 调用 Windows 原生命令实现。

优点：

- 与现有 `others` 目录风格一致

- 最接近原始 PowerShell 使用方式

- 迁移成本最低，后续维护简单

缺点：

- 如果未来需要批处理或无交互调用，还需要补充参数模式

#### 方案二：单文件脚本，同时支持交互和命令行参数

这种方式会在脚本内部加入参数解析，兼顾交互式和自动化调用。

优点：

- 扩展性更好

- 更容易接入其他自动化流程

缺点：

- 超出当前“等价迁移”的范围

- 交互与参数两套入口会增加实现复杂度和测试成本

#### 方案三：多文件模块化实现

这种方式会拆分为入口脚本、系统操作模块、公钥处理模块、测试模块。

优点：

- 结构更清晰

- 单元测试更容易组织

缺点：

- 不符合当前“单文件脚本”的明确约束

- 对 `others` 目录现有工具风格侵入较大

### 推荐方案

采用方案一：单文件交互式 Python 脚本。它最符合当前目录风格、用户偏好和这次迁移的目标边界，能在最小改动范围内完成 PowerShell 到 Python 的等价替换。

### 脚本结构设计

脚本文件定为：

```text
D:\GitHub\pythontools\others\start_ssh.py
```

脚本内部按职责拆成有限的几个函数，但全部保留在同一文件中：

- 权限检查函数：确认当前进程具有管理员权限

- 命令执行函数：统一调用 PowerShell 或其他系统命令，并处理错误输出

- OpenSSH 安装函数：检查 capability 状态，必要时安装 `OpenSSH.Server~~~~0.0.1.0`

- SSH 服务配置函数：检查 `sshd` 服务状态、启动服务、设置自动启动

- 防火墙配置函数：检查并创建 `sshd` 规则

- 公钥处理函数：负责标准化公钥、创建 `.ssh` 目录、创建和写入 `authorized_keys`、避免重复写入

- cpolar 检查与启动函数：检测命令是否存在、检查是否已有 `tcp 22` 进程、必要时启动或打开官网

- 主流程函数：串联整个执行顺序并负责中文输出

### 数据流与执行流程

主流程按以下顺序执行：

1. 启动脚本后先检查管理员权限

2. 非管理员则打印提示并退出，返回非 0

3. 查询 `OpenSSH.Server~~~~0.0.1.0` 是否已安装，未安装则执行安装

4. 查询 `sshd` 服务，未运行则启动，并将启动类型设为自动

5. 查询名为 `sshd` 的防火墙规则，不存在则创建入站 TCP 22 规则

6. 提示用户输入要授权的 SSH 公钥；用户直接回车时跳过写入

7. 规范化公钥内容，写入 `~/.ssh/authorized_keys`，避免重复添加

8. 检查 `cpolar` 是否可用；若不可用则打开 `https://www.cpolar.com/` 并结束流程

9. 若 `cpolar` 可用，则检查当前是否已有匹配 `tcp 22` 的 `cpolar` 进程；如果没有，则执行 `cpolar tcp 22`

10. 输出本次执行结果

### 关键实现决策

#### Windows 系统操作通过 subprocess 调用原生命令

Python 不直接替代 Windows capability、服务和防火墙管理能力，而是作为编排层，使用 `subprocess.run()` 调用 PowerShell 或系统命令。

这样做的原因是：

- 与现有脚本行为最接近

- 不需要额外第三方依赖

- 在 Windows 场景下更稳定，兼容系统自带管理接口

#### 公钥写入逻辑保留原语义

公钥处理逻辑将严格保留 PowerShell 版本的语义：

- 输入先做 `strip()`

- 为空则返回 `EmptyInput`

- 若 `~/.ssh` 不存在则自动创建

- 若 `authorized_keys` 不存在则自动创建

- 已存在完全相同的一行公钥时，不重复写入，返回 `AlreadyExists`

- 成功新增时返回 `Added`

这部分将做成纯 Python 文件逻辑，避免依赖外部命令，便于单元测试。

#### cpolar 行为保持原样

`cpolar` 的处理逻辑不做产品化改造，只做等价迁移：

- 找不到 `cpolar` 命令时，打开官网并立即结束

- 找得到时，检查是否已有命令行包含 `tcp 22` 的 `cpolar` 进程

- 没有则直接执行 `cpolar tcp 22`

这里不会引入“仅提示不启动”之类的新分支，避免行为偏移。

### 错误处理

脚本采用“失败即退出”的处理策略，避免系统处于半完成但不明确的状态。

错误处理规则如下：

- 管理员权限不足：打印中文提示并退出

- OpenSSH capability 查询或安装失败：打印失败原因并退出

- `sshd` 服务查询、启动或设置自动启动失败：打印失败原因并退出

- 防火墙规则查询或创建失败：打印失败原因并退出

- `cpolar tcp 22` 启动失败：打印失败原因并退出

- 打开官网失败：打印提示，但不额外重试

公钥写入不是阻塞整个系统初始化的前置条件；如果用户直接回车，则脚本继续执行 `cpolar` 检查逻辑。

### 测试设计

本次测试分为两层：

#### 单元测试

优先覆盖最稳定、最适合自动化的逻辑，即公钥处理函数。测试点包括：

- 新公钥首次写入时自动创建 `.ssh/authorized_keys`

- 相同公钥重复写入时不重复添加

- 带首尾空白的输入会被规范化

- 空字符串输入返回跳过状态

测试方式使用 Python 标准库 `tempfile` 与 `pathlib`，在临时目录下运行，不污染真实用户目录。

#### 手工验证

系统级流程通过手工验证，验证内容包括：

1. 非管理员运行时是否直接退出

2. 管理员运行时是否能正确安装或识别 OpenSSH Server

3. `sshd` 服务是否能被启动并设置为自动

4. 防火墙规则是否会按预期创建

5. 公钥写入是否符合去重逻辑

6. `cpolar` 不存在时是否打开官网

7. `cpolar` 存在且未运行时是否启动 `tcp 22`

### 兼容性与依赖

- 目标运行平台为 Windows

- 依赖 Python 标准库，不引入第三方包

- 依赖系统可用的 PowerShell 和 Windows 管理命令

- 依赖 `cpolar` 已安装并可从 PATH 访问，除非用户接受官网引导逻辑

### 风险与缓解

- Windows 不同版本上 capability 或服务命令输出可能略有差异  
  缓解方式：优先使用稳定字段和最小必要命令，并对输出做保守判断。

- 用户 PATH 中不存在 `cpolar`，但实际已安装  
  缓解方式：保持与原脚本一致，检测失败即打开官网，不额外猜测安装路径。

- 系统命令失败时错误信息可能不够直观  
  缓解方式：统一封装命令执行函数，把 stderr/stdout 归并为中文失败信息输出。

- 仓库当前没有现成测试框架规范  
  缓解方式：先补最小可运行的 Python 测试文件，保证核心纯逻辑可验证。
